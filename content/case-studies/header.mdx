## Context

Header turns the feeds a user already follows (RSS, YouTube channels,
newsletters, Reddit, X) into LLM-written briefings against user-defined goals.
There is also a feature called Link Bankruptcy: paste a pile of saved URLs and
get one briefing that triages them. The stack is async Python with FastAPI and
PostgreSQL on the backend, a React Native/Expo app on the frontend, and a
three-stage LLM pipeline with six providers behind an adapter layer.

I joined as a software engineer intern in June 2026. This is the closest thing
on this site to plain production software engineering: features built, reviewed,
and merged into a living codebase with 100+ API endpoints, dozens of
migrations, and real users. Eight merged PRs so far, and the two biggest are
below.

## Briefing customization

Users had no control over what a briefing looked like. I built per-goal layout
control end to end: drag to reorder sections, toggle each one on or off, set
per-section detail, a TLDR pinned to the top, and a computed read time on
every briefing.

The schema decision was one nullable JSONB column on the goals table, with no
default and no backfill. NULL means "use the current default," resolved in code
at read time, so improving the default later is a code change instead of a data
migration across every existing row. The trade-off is that nothing in the
database enforces valid section keys, which is why the API-layer validator is
as strict as it is.

The prompt refactor was the hard part. The old generation prompt hardcoded
every section. I broke it into per-section instruction blocks that are
order-independent by construction: each block opens with its own heading and
carries its own inclusion conditions, and detail level is injected per block
rather than as one global directive. An assembler filters to the enabled
sections in the user's order and splices the result into the prompt template.
The TLDR is deliberately not one of these blocks. It is a second LLM pass over
the finished body, which is also why it cannot be reordered: it summarizes the
thing it sits above. A normalizer pins it first even against a hand-crafted API
payload, and the frontend's drag lock is a mirror of that rule, not the
enforcement.

Rollout went through a default-off feature flag, and I froze the old prompt
as a literal file copy, so with the flag off the pipeline reproduced
pre-feature behavior exactly. That made the merge itself a no-op. The flag has
since been flipped on, and the feature is live in production.

## A history feature shaped by a cascade

Link Bankruptcy briefings were hidden from the normal dashboard, so a user who
lost the direct URL had no way back to a past submission. I added a paginated,
authenticated history endpoint and a history screen listing every past
briefing with its status and URL count.

The interesting constraint was underneath. Each submission provisions an
ephemeral goal, and a cleanup hook later soft-deletes the sources behind it.
That hook leaves the goal row alone for one reason: the briefing's foreign key
is ON DELETE CASCADE, so deleting the goal would take the briefing with it. The
consequence for history is that you can join briefings to goals but not to
sources, so the URL count the screen needs cannot be computed at read time. The
fix was to denormalize it into the briefing's JSONB stats before generation
starts, ahead of both the completed and the failed terminal paths. That
surfaced a second bug: the completion path rebuilds stats from an explicit
allowlist of keys, so the new key had to join that allowlist or it would be
silently erased the moment a briefing finished.

Pagination is bounded limit/offset with a separate count query. Offset
pagination drifts when rows are inserted mid-scroll, and for per-user history
at this scale keyset pagination would have been over-engineering. I would
revisit that choice if the row counts grew.

## The regression I shipped

My default section order moved "What to do" from last place to second. Two
strip functions, one on the briefing page and one in the email path, truncated
the summary from that heading to the end of the string, which was only correct
while the section was last. With my layout flag on, they amputated roughly 60%
of the briefing body. I fixed both to cut to the next section heading instead,
wrote 18 tests for the pair, then swept every other function that touched the
summary for the same positional assumption. The sweep found none, which is the
outcome you want but cannot assume.

## Testing

Roughly 8,600 merged lines, and 54% of them are tests. Around 420 test
functions across this work: 266 live in nine files I created on the main
branch (257 pass, 9 skip), and the rest sit in files I extended and on
branches still in review.

The piece I would defend hardest in an interview is a DNS guard for the test
suite. A mocked HTTP call in a unit test had rotted after a refactor and fell
through to a real DNS lookup, staying green only because the dev box had
internet. The guard intercepts hostname resolution at the socket layer and
fails any unit test that reaches for the network, with a narrow pass-through
for local test fixtures. It snapshots the real resolver at import time, before
any test can monkeypatch it, so a rotted mock cannot shadow it the way the
original one did.
